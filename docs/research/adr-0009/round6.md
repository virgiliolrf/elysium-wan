## 1. The sparse-MoE classifier by routing structure (D8, finding d)

- Round 5 kept a parameter-rank clause (rank ≥ 3 with the expert count leading). It is a shape test, not a routing
  test: a dense family whose 3-D parameter happens to lead with a number equal to a config key would be refused, and a
  `Conv1d` weight (C, 1, k) (mamba, falcon_h1, `round5.md` §1) is only spared by the coincidence that C ≠ E.
- CODE (5.19.0): routing is a selection over the expert dimension whose indices choose expert parameters or expert
  modules. `MixtralTopKRouter.forward` runs `torch.topk(router_probs, k, dim=-1)` over E (`modeling_mixtral.py:103-110`);
  `MixtralExperts.forward` turns the indices into `one_hot(top_k_index, E+1)`, `where`, and indexes
  `self.gate_up_proj[expert_idx]` (`:68-92`); `MixtralSparseMoeBlock.forward` passes the indices from `gate` to
  `experts` (`:126-127`). Qwen2/3-MoE are the same (`modeling_qwen2_moe.py:343-344`, `modeling_qwen3_moe.py:278-279`).
- Rule (normative text in SPEC-model §2): the classifier runs one forward of the gate's tiny model before the class
  swap, with the trace's function-mode spy, on the CPU. E is the config's expert count (one of `num_local_experts`,
  `num_experts`, `n_routed_experts`, `moe_num_experts`; E ≥ 2; a config with none has no MoE). A *selection* is a call
  of `topk`, `sort`, `argsort`, `argmax`, `max` with indices or `multinomial` over a dimension of size E; its index
  outputs are tagged, and every tensor computed from a tagged tensor is tagged. A module M is sparse-MoE when, inside
  its forward, a selection's tagged output indexes (`__getitem__`, `index_select`, `gather`, `one_hot`, `where`,
  `nonzero`, `index_add_`, `scatter*`, `bincount`) a parameter whose leading dimension is E, or M has a `ModuleList`
  child of E ≥ 2 members of which a subset is called after the selection; the block is the innermost such M. Its class
  is looked up by exact name in SUBSTITUTE; no row refuses the model. A router or experts child with a row is admitted
  only under a block with a row.
- Consequences: mamba, falcon_h1, falcon_mamba, lfm2, recurrent_gemma, olmo_hybrid, qwen3_5_text (`Conv1d`) and rwkv
  (rank-3 mixing vectors) make no selection over E: dense, admitted (E1's mamba and falcon_h1 arms). Mixtral, Qwen2/3-
  MoE: their `*SparseMoeBlock` (rows exist). jamba, llama4_text, gpt_oss, deepseek_v3, phimoe, olmoe: classified,
  refused (no row; phimoe's RNG router is refused by the trace's draw check first). A missed MoE (a routing pattern the
  tags do not follow, e.g. indices turned into Python ints by `.item()` without a `ModuleList` of E) runs HF's own block
  on both sides of the gate and is gated as any dense module: never silently different from vanilla on the gate's map.
- Cost: one CPU forward of the tiny model at launch, inside the gate's existing 1–2 s (HYPOTHESIS); 0 per step.

## 5. Admission re-checks the device-map refusal (decision 8, finding h)

- CODE: SPEC-control §2.3 step 2 (`find_replacement`) falls back from the identical model to the region;
  RUNTIME-I15 admits a same-type move between GPU models; round 5 added a class filter for heals only.
- Rule (normative in CONTROL-I24, SPEC-control §2.3, RUNTIME-I15): every admission (first launch, heal, restart,
  rebalance, resume) re-evaluates decision 8 on the map it would build, from the gate reports of the nodes then in
  the pool: each slot's device class equals its recorded class, and some node of the current pool holds every class
  of the map among its CPU and slot devices; otherwise the admission is refused naming the classes, a heal fails
  cleanly, and nothing relaunches. Gate, fingerprint and torch RECORD alone never admit.
- Cost: 0 per step; an admission reads recorded gate reports (ms). Availability: a heal or restart needs a spare of
  the slot's class and a pool that still holds the map whole.

## 6. The bytecode prefix and import order (D5, D9, finding i)

- CODE: `src/wantrain/model/hf.py:17` imports torch at module top; `hfm` will live in the same package; the worker
  starts stages as `python -m wantrain.worker.stage_main` (`src/wantrain/worker/agent.py:535`), whose module top
  imports only the standard library (`stage_main.py:14-21`).
- MEASURED (`round5.md` §3): `-X pycache_prefix=<fresh>` on the command line: 0 of 726 torch modules on in-tree `.pyc`;
  `sys.pycache_prefix` assigned after `import torch`: 726 of 726. `PYTHONPYCACHEPREFIX` exported into the already
  running interpreter leaves `sys.pycache_prefix` None (Evidence 17).
- Choice: the prefix is an interpreter-start fact, never an import-order fact. The worker passes `-X
  pycache_prefix=<fresh per-launch dir>` on every stage and buffer-builder command line; nothing assigns
  `sys.pycache_prefix` or exports `PYTHONPYCACHEPREFIX`. The guard (`hfm.guard_environment`) checks rather than sets,
  so it may run after torch's import: it asserts `sys.pycache_prefix` equals the launch's directory and that every
  module already in `sys.modules` from torch, transformers or `wantrain` has `__cached__` under it (a sourceless `.pyc`
  refuses). A process started without the flag has torch's in-tree `.pyc` loaded and is refused, never trusted. So
  torch's `.pyc` need no fingerprint: none is ever read.
- Cost: 0 per step; compiling the imports once per launch, 1–4 s (HYPOTHESIS, E6).

## 7. Native libraries in the fingerprint (D9, R18, finding j)

- CODE/FACT: Linux CUDA wheels load cuBLAS, cuDNN, NVRTC (and NCCL when used) from `nvidia-*` distributions through
  torch's `RUNPATH` (`$ORIGIN/../../nvidia/...`); glibc searches `LD_LIBRARY_PATH` before `DT_RUNPATH`, so a variable
  can substitute any of them; a library without a `RUNPATH` resolves through `ld.so.cache`. On macOS torch's dylibs
  (`torch/lib/libtorch_cpu.dylib`, `libc10.dylib`, `libomp.dylib`, …) are inside the torch wheel, and system libraries
  (Accelerate, libSystem, Metal/MPS) are images of the dyld shared cache with no file on disk.
- What is hashed (normative in MODEL-I10): after the gate has run on the CPU and the slot's device (so lazily loaded
  kernels libraries are in), the guard lists every loaded native object: Linux, the file-backed executable mappings of
  `/proc/self/maps`; macOS, `_dyld_image_count`/`_dyld_get_image_name` (ctypes, libSystem). Each object is either
  (a) a file listed in a fingerprinted distribution's RECORD (torch, transformers, the `nvidia-*` and other wheels torch
  requires in `uv.lock`), tied by path and `(st_dev, st_ino, size)` to the file the RECORD check hashed (no second
  hash); a loaded object whose basename is in such a RECORD but whose path is not refuses (shadowing); or (b) any
  other object (the interpreter, libc, libm, libstdc++, the CUDA driver `libcuda.so`): its path and sha256 are
  recorded; on macOS a shared-cache image is recorded as (image name, `_dyld_get_shared_cache_uuid`, `kern.osversion`).
  The (b) set must be equal on every node of the same (platform tag, device class) and, at heal, restart, rebalance
  or resume, equal to the slot's recorded set (CONTROL-I24).
- gpu=false, checked now: the macOS arm (dyld list; torch's dylibs against RECORD; shared-cache UUID) on this Mac, and
  the Linux CPU arm (`libtorch_cpu.so`, `libgomp`, libc, libm from `/proc/self/maps`) in CI; E6 plants a copy of a
  torch library loaded from another path (refused) and a changed (b) entry between two nodes (refused). Pending (M1,
  gpu true): the `nvidia-*` libraries and `libcuda.so` on CUDA hosts.
- Cost: (a) costs stat calls; (b) hashes tens of MB on CPU hosts and ≈ 0.1–0.2 GB with the CUDA driver, < 0.5 s per
  launch (HYPOTHESIS); 0% of step time.
- What stays open (R18, narrowed): (b) objects are compared across nodes, not against a source of truth (two nodes
  with the same altered libm agree); other Python distributions outside the fingerprinted set (an import-closure
  fingerprint is a FOLLOW-UP).
